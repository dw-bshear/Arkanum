# Arkanum 1.1.0

## Scope

This minor feature release adds encrypted credential version history and administrator-configurable user feedback, requires descriptions for newly created vaults, and removes the temporary settings control-surface statement. Application/assembly metadata and CLI/GUI/package defaults use 1.1.0. Historical releases and security assessments remain immutable and do not assess these changes.

Source publication is separate from tagging, downloadable installer publication, installation and production acceptance. This document is not evidence that a Coverity scan has run or that native Windows acceptance is complete.

## Vault descriptions

New vaults require a nonblank description, enforced both by the form and the server. Automatically created personal vaults use the account display name (falling back to username):

> Alex Example's personal vault. Invite other users if you want to share your entries.

When an existing personal vault is next ensured, only a blank description or the original shipped default description is replaced. Custom descriptions and vault contents are preserved.

## Credential editing and saved versions

Expand a credential and choose **Edit credential** to change its title, username, folder or password. Leaving the new password blank preserves the existing password. **Saved version history** lists the five most recent saved versions, newest first, **including the current version** (not five previous versions plus current). Each version requires an explicit reveal; an ordinary page load does not render historical passwords. History snapshots encrypt the saved title, username and password together. Legacy credentials preserve their original value on first edit; values overwritten before this feature existed cannot be reconstructed.

### Existing SQL Server databases

The new `CredentialVersions` table and its least-privilege permissions must be installed before the new application is put into service. Back up the database first, stop application writes during the controlled change, and run the **new version's** `--database-setup provision` command with the approved setup identity and existing runtime login/password. This command applies idempotent shipped schema and grants; it does not replace existing runtime credentials or the Recovery Key. Run `--database-setup preflight` using the runtime connection and matching Recovery Key before app replacement. See `windows-server-2022-setup.md` for setup inputs. Missing schema fails preflight rather than being silently created by the runtime SQL identity. Existing SQLite fallback files receive the additive history table at startup.

## Configuring user feedback

In **Settings → Notifications**, an administrator can enable the feedback button, enter one destination email address, and enter up to five optional questions (one per line, maximum 250 characters each). Feedback is **off by default**. Configure the existing SMTP settings before enabling it.

Authenticated users open **Feedback** in the upper-right header. The modal allows 1–1000 characters of feedback, optional answers of up to 500 characters each, and up to two PNG/JPEG screenshots of at most 2 MiB each (4 MiB combined). Files are size/signature checked, given generated attachment names and sent from memory; uploads are not stored in the webroot or on disk. The recipient is looked up server-side, never accepted from the user request or included in the user form/JSON response. Users receive a generic result rather than SMTP diagnostics. Success means the configured SMTP server accepted the message, not that final inbox delivery is proven.

One attempt per account per minute limits repeat submissions. This limit is process-local; multi-instance installations also need a shared gateway limit. Screenshots are not antivirus-scanned or redacted automatically. Users must remove secrets before submitting them.

## Operational boundaries

- Keep the existing database and matching Recovery Key; history depends on the same encryption boundary as current credentials.
- Back up the database and application/configuration before schema updates or app replacement. Follow the controlled SQL setup path rather than granting schema rights to the runtime identity.
- Feedback uses the administrator-configured SMTP service. Enable feedback only after reviewing its recipient and mail configuration. Do not include passwords, Recovery Keys, connection strings or other secrets in feedback text or screenshots.
- Repository visibility remains unchanged. Feedback is not submitted to GitHub, and this feature does not register the project with Coverity Scan.

## Verification

Verified locally with the pinned .NET SDK:

- Complete .NET regression suite: 266 passing tests; Python suite: 72 passing tests.
- Release publish build and disposable authenticated SQLite checks for credential edits, encrypted retention, selected-version reveal, no-cache responses and denied forged version IDs.
- `tests/feature_110_smoke.py`: published-app HTTP checks for required descriptions, personalized vault copy, removed settings copy, admin-only feedback configuration, recipient secrecy, authentication/antiforgery, real loopback SMTP/MIME screenshot delivery, cooldown, length enforcement and disabling stale forms.
- `tests/credential_history_sql_smoke.py`: actual disposable SQL Server additive upgrade, missing-schema preflight rejection, repeated provisioning without current-ciphertext changes, and encrypted history edit/reveal/pruning through the limited runtime login.
- `tests/sql_setup_smoke.py`: real SQL schema/login provisioning, least-privilege preflight, wrong-password rejection, production web startup/liveness and correct/incorrect Recovery Key checks.
- Chromium desktop light/dark and mobile modal checks, including Escape/focus restoration and no horizontal overflow.

These tests use disposable data and loopback mail only. Organization-specific SMTP delivery, native Windows/IIS installation, Coverity Scan and a new release-specific security assessment are separate acceptance checks and are not claimed here.
